# Web UI

This directory builds the repository catalog and every tracked tool and example README
into static HTML. The output in `dist/` needs no application server and can be served by
GitHub Pages, a container, or any static file host. There is no client-side framework and
no runtime dependency: `package.json` lists only build-time devDependencies (`marked` for
markdown, `shiki` for syntax highlighting, and the `@fontsource-variable` font files), and
what ships to the browser is plain HTML, CSS and two small hand-written scripts.

Nothing about a tool or example is hand-listed here. The catalog is generated by walking
`tools/<category>/<tool>/README.md` and `tools/<category>/<tool>/examples/<platform>/README.md`
in the repository tree; see "Adding a tool or example" below.

## Build configuration

The build accepts two independent environment variables, resolved once by
`resolveConfig()` in `src/lib/config.mjs` and threaded through the rest of the build as an
explicit argument — there is no mutable module-level state:

| Variable | Purpose | Default |
|---|---|---|
| `SITE_URL` | Public URL used by canonical links, structured data, the sitemap, and `robots.txt` | `https://hambn.github.io/tool-containers` |
| `BASE_PATH` | Optional prefix added to internal links and local assets | Empty |

The two are independent. A custom domain sets only `SITE_URL`:

```bash
SITE_URL=https://docs.example.com npm run build
```

A subpath deployment sets both, so canonical URLs stay correct while every internal link
and asset path carries the prefix:

```bash
SITE_URL=https://example.com/tool-containers \
BASE_PATH=/tool-containers \
npm run build
```

For a local or container-served build at the domain root:

```bash
SITE_URL=http://localhost:4173 npm run build
python3 -m http.server 4173 --directory dist
```

`SITE_ORIGIN` remains a compatibility alias for `SITE_URL`. New deployments should use
`SITE_URL`.

## Commands

Install dependencies, build the static files, and verify the generated route inventory:

```bash
npm ci
npm run build
npm test
```

`npm test` (`test.mjs`) re-derives the expected page set directly from the `tools/` tree
— independently of the generator's own bookkeeping — and checks the built `dist/`
against it: every expected route exists and nothing extra was built, the sitemap matches,
every page has exactly one `<h1>`, a unique title and description, canonical/Open
Graph/JSON-LD tags, no internal link is broken, and no route leaks a `BASE_PATH` prefix
when one was not requested. Run it after building with the same environment variables
used for that build.

## Directory layout

```
web-ui/
├── src/
│   ├── build.mjs    # Orchestrating entry point: resolves config, renders every page,
│   │                # emits shared assets, sitemap and robots.txt
│   ├── lib/         # Pure, reusable modules: config, catalog, markdown rendering,
│   │                # syntax highlighting, icons, asset emission, SEO, page shell
│   ├── pages/       # One file per page kind: home, docs (index/tool/example), 404
│   ├── client/      # Browser-side scripts, shipped as real files: theme (inline,
│   │                # pre-paint) and site (deferred progressive enhancement)
│   └── styles/      # base.css (tokens, reset, shared primitives) plus one
│                    # stylesheet per area (home.css, docs.css)
├── public/          # Checked-in branding assets copied verbatim into dist/:
│                    # favicon, apple touch icon, OG image, webmanifest
├── test.mjs         # Build verification: re-derives the expected page set from
│                    # tools/ and checks dist/ against it
└── dist/            # Build output (generated, not tracked)
```

## Content flow

Every page is generated from a document tracked elsewhere in the repository — nothing is
hand-listed:

- `src/lib/catalog.mjs` walks `tools/<category>/<tool>/README.md` and
  `tools/<category>/<tool>/examples/<platform>/README.md` to build the catalog and the
  page list. A category directory is kept even if empty; a tool or example only becomes
  a page once it has a `README.md`.
- `src/build.mjs` reads each source document once and passes it to `src/lib/markdown.mjs`,
  which rewrites repository-relative links into site routes (or GitHub links for
  untracked-as-pages files), extracts and highlights fenced code with `src/lib/highlight.mjs`,
  and renders the result to HTML.
- `src/lib/seo.mjs` derives the title, meta description and JSON-LD structured data for
  each page from that same document: a shared `@graph` of Organization/WebSite nodes, plus
  `SoftwareApplication` on tool pages and `HowTo` on example pages.
- `src/pages/home.mjs` and `src/pages/docs.mjs` lay the rendered content into the page
  shell from `src/lib/layout.mjs`.

CSS and JavaScript are shared, content-addressed assets — `dist/assets/site.<digest>.css`
and `dist/assets/site.<digest>.js` — rather than inlined into every page, so the browser
downloads each once for the whole site and the digest in the filename makes them safe to
cache immutably. Only the pre-paint theme script (applies the stored color scheme before
first render, to avoid a flash) and a per-page subset of the icon sprite are inlined into
each page.

## Adding a tool or example

Nothing under `web-ui/` needs to change. Add the directory and `README.md` under
`tools/<category>/<tool>/` (and `tools/<category>/<tool>/examples/<platform>/README.md`
for a runnable example); the next build discovers it, generates its page, and lists it in
the catalog and sitemap automatically.
